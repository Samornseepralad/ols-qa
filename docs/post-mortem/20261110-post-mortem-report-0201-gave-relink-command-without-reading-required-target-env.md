## สรุปสั้น (Executive Summary)

ระหว่างรีเทส OLS-1001 บน dev session ของบัญชีทดสอบหมดอายุ ผมส่งคำสั่ง relink ให้เจ้าของงานรันตามแม่แบบในขั้น 4b โดยไม่ได้เปิดสคริปต์ `session_relink_dev.js` ดูก่อน สคริปต์บังคับให้ตั้งตัวแปร `OLS` และไม่มีค่าเริ่มต้นโดยตั้งใจ (`session_relink_dev.js:266`) คำสั่งจึงล้มทันทีด้วยข้อความ "set OLS to the dev host" เจ้าของงานต้องรันซ้ำ แก้ที่ต้นเหตุโดยใส่คำสั่ง relink/mint ที่ตรวจแล้วลงในคู่มือโปรเจกต์ และเพิ่มกฎ "อ่านวิธีใช้ของสคริปต์ก่อนยกคำสั่งให้คนอื่นรัน"

## 1. ปัญหา (Problem Statement)

- ผมส่งคำสั่ง `node capture/session_relink_dev.js --force <tag>` ในลูป `for` ให้เจ้าของงานรัน คำสั่งไม่มี `OLS=` นำหน้า
- เจ้าของงานรันแล้วได้ `<tag> FAILED (log: …)` ไม่มีรายละเอียดบนจอ
- log (221 bytes) ระบุ: `session_relink_dev: set OLS to the dev host … There is no default: guessing one has already sent probes at a hands-off environment.`
- ที่มาของข้อบังคับ: `capture/session_relink_dev.js:266` เรียก `requireTarget(process.env.OLS, …)`

**สิ่งที่ควรจะเป็น:** คำสั่งที่ยกให้คนอื่นรันต้องตรวจก่อนว่ารันได้จริง — `docs/ENVIRONMENT.md` ข้อ "คำสั่งที่ยกให้คนอื่นรัน ต้องเทียบ env ก่อนส่ง" และ memory `slow-and-correct-over-fast` (ตรวจคำสั่งก่อนรันหรือส่ง)

## 3. สาเหตุโดยละเอียด (Root Cause Analysis)

จุดตัดสินใจที่ผิดคือการประกอบคำสั่งจาก **แม่แบบทั่วไป** (`<relink-command> --env <env> --account <account>`) แทนที่จะอ่านวิธีใช้จริงของเครื่องมือของโปรเจกต์นี้ ซึ่งใช้ `--force <tag>` + ตัวแปร `OLS` ทั้งสองรูปแบบต่างจากแม่แบบ ผมอ่านหัวสคริปต์ครึ่งเดียวแล้วพอใจ เพราะข้อความหัวไฟล์ตอบคำถามเรื่องรหัสผ่านที่กำลังหาอยู่

### 5 Whys

1. **ทำไมคำสั่งล้ม?** — เพราะไม่ได้ตั้งตัวแปร `OLS` ที่สคริปต์บังคับ
2. **ทำไมไม่ได้ตั้ง?** — เพราะผมประกอบคำสั่งจากแม่แบบทั่วไป ซึ่งไม่มีช่องสำหรับตัวแปร env นี้
3. **ทำไมใช้แม่แบบทั่วไปโดยไม่ตรวจกับสคริปต์จริง?** — เพราะคู่มือโปรเจกต์ไม่มีคำสั่ง relink/mint ของ dev ที่ตรวจแล้ว (`references/ols-project-guide.md` ไม่มีบรรทัดนี้) จึงต้องแปลงแม่แบบเอง
4. **ทำไมไม่อ่านสคริปต์ให้ครบก่อนยกให้คนรัน?** — เพราะไม่มีขั้นบังคับ "เปิดวิธีใช้/ตัวแปรที่ต้องมีของสคริปต์ก่อนส่งคำสั่ง" ในขั้น 4b และผมถือว่าการอ่านหัวไฟล์พอ
5. **ทำไมไม่มีขั้นบังคับนั้น?** — เพราะ workflow ถือว่าคำสั่งใน 4b มาจาก "intake answers / project guide" แต่ไม่มีอะไรตรวจว่าค่าเหล่านั้นถูกเติมครบจริง ช่องว่างนี้ปิดได้ด้วยการเก็บคำสั่งที่ตรวจแล้วไว้ในคู่มือโปรเจกต์ (ทั้งคลาส)

**ทำไมชั้นป้องกันที่มีอยู่ถึงไม่จับ:** สคริปต์ปฏิเสธถูกต้อง (fail-closed) แต่ผลที่ปลายมือคนรันเป็นแค่ `FAILED` บรรทัดเดียว ไม่มีชั้นใดตรวจคำสั่งก่อนส่ง

## 5. แนวทางการแก้ไข (Fix)

- ส่งคำสั่งที่แก้แล้ว (เติม `OLS=https://<DEV_HOST>`) ให้เจ้าของงาน
- เพิ่มคำสั่ง relink ที่ตรวจกับสคริปต์จริงไว้ใน `references/ols-project-guide.md` (หัวข้อ login by command ของ dev)
- เพิ่มกฎใน `docs/ENVIRONMENT.md`: ก่อนยกคำสั่งให้คนรัน ต้องอ่านตัวแปร/อาร์กิวเมนต์ที่สคริปต์บังคับจากตัวสคริปต์

**ยืนยันแล้วด้วย:** อ่าน `/tmp/relink-<tag>.log` ได้ข้อความข้างต้น และ `grep` พบบรรทัดบังคับที่ `session_relink_dev.js:266` · หลังเจ้าของงานรันคำสั่งที่แก้แล้ว session ใช้งานได้ (`session_verify.js` ผ่าน 1/1)

## 7. การตรวจจับปัญหา (Detection)

- **ใครจับได้ / จับได้ยังไง:** เจ้าของงานเห็น `FAILED` แล้ววางผลกลับมา ผมอ่าน log ได้สาเหตุทันที
- **ใช้เวลาเท่าไหร่กว่าจะรู้:** 1 รอบการส่งคำสั่ง-รัน-ส่งผลกลับ (ระยะเวลาไม่ได้วัด)
- **รอบหน้าอะไรจะจับได้เร็วกว่านี้:** คำสั่งที่ตรวจแล้วในคู่มือโปรเจกต์ (P1) ทำให้ไม่ต้องประกอบเอง

## 8. บทเรียนที่ได้ (Lessons Learned)

### สิ่งที่ทำได้ดี
- สคริปต์ปฏิเสธแบบ fail-closed ไม่ยิงไปที่ env ที่ไม่ได้ตั้งใจ
- ผมเรียกสกิลสืบสวนและอ่าน log ก่อนเสนอทางแก้

### สิ่งที่ต้องปรับปรุง
- อ่านสคริปต์ให้ครบส่วนที่บังคับค่าก่อนยกคำสั่งให้คนอื่นรัน
- เห็นว่ามีผล `curl` รหัส 000 แล้วสรุปว่าเข้า dev ไม่ได้ ทั้งที่มี memory ระบุว่าเป็นปัญหาความเชื่อถือใบรับรองของ curl ในเครื่องนี้ — ผมแก้ข้อสรุปนี้ในรอบเดียวกันหลังตรวจด้วย `-k` (ได้ 200) แต่ควรเช็ค memory ก่อนพูด
